# Parallel worktree Dev Containers design

Date: 2026-07-25  
Status: approved for planning

## Problem

Multiple agents need to work on this repository concurrently. Git worktrees
isolate source changes, but agents still share the host Python environment,
dependency state, process ports, and test runtime. That makes one agent's setup
or running application capable of interfering with another's.

Each worktree needs a reproducible development container in which an agent can
run the CI-equivalent quality gate and, when needed, launch Streamlit against
the host's existing Ollama installation.

## Goals

- Give every linked worktree its own app container, Compose project, network,
  runtime state, and dynamically assigned Streamlit host port.
- Support both a helper-driven workflow for agents and the normal Cursor or VS
  Code "Reopen in Container" workflow.
- Match the repository's Python 3.11 development and CI environment.
- Run `./scripts/run_ci_checks.sh full` inside every container.
- Support live Streamlit testing from each worktree.
- Share the host Ollama service and model store to avoid duplicating large
  models and memory use.
- Preserve normal Git operations, including commits and repository-owned hooks,
  from inside linked-worktree containers.
- Cache dependency layers so repeated worktree setup is reasonably fast.

## Non-goals

- Running a private Ollama service per worktree.
- Downloading Ollama models automatically.
- Configuring GPU passthrough.
- Supporting remote Docker hosts.
- Sharing Chroma state between worktrees.
- Automating corpus PDF ingestion or OCR in the container workflow.
- Automatically deleting branches or worktrees during container cleanup.

## Decisions

- Use Docker Compose as the runtime owner and attach the Dev Container to its
  `app` service.
- Keep one committed base service definition; do not duplicate the environment
  between Compose and Dev Container configuration.
- Keep the development service alive with an idle command. Start Streamlit on
  demand rather than making it the container's default process.
- Publish container port `8501` through a dynamically allocated host port.
- Set `ASTRO_OLLAMA_HOST` to `http://host.docker.internal:11434`.
- Add Linux compatibility with the `host-gateway` mapping; Docker Desktop for
  macOS resolves `host.docker.internal` directly.
- Create managed worktrees below the repository's `.worktrees/` directory and
  gitignore that directory.
- Derive a sanitized Compose project name from the repository and worktree
  slug. The helper passes it explicitly to Compose.
- Keep `chroma_db/`, logs, caches, and other gitignored runtime artifacts in
  the individual worktree.

## Architecture

```text
host Ollama :11434
        ▲
        │ shared HTTP endpoint
        │
worktree A ── Compose project astro-<slug-a> ── app container
        │              └── dynamic host port → container :8501
        │
worktree B ── Compose project astro-<slug-b> ── app container
                       └── different dynamic host port → container :8501
```

Every Compose project has independent container and network names. Each app
service bind-mounts only its worktree as the working source tree. Therefore
gitignored data generated by the application remains worktree-local.

The linked worktree's `.git` file points to metadata under the primary
checkout's Git common directory. Mounting only the worktree would leave that
absolute host path unavailable inside the container. A host-side initialization
step resolves `git rev-parse --git-common-dir` and creates a gitignored local
Compose override that bind-mounts the resolved directory at the same absolute
path in the container. This preserves `git status`, commits, branches, and
hooks without copying Git metadata. The generated override belongs to the
specific worktree and is never committed.

The base image installs Python 3.11, required operating-system packages, and
the pinned development dependencies. Dependency manifests are copied before
the source layer so changes to application code do not invalidate the
expensive dependency installation. The worktree is installed editable during
container setup.

## Components

### Container image

The image provides:

- Python 3.11.
- System libraries required by this repository's Python dependencies.
- Git and basic development utilities.
- Packages from `requirements-dev.txt`, which includes runtime requirements.
- An environment capable of running the shared CI gate and Streamlit.

The image must run as a non-root development user whose ownership is compatible
with files created in the bind-mounted worktree.

### Compose service

The committed Compose definition contains one `app` service. It:

- Builds the development image.
- Mounts the current worktree at a fixed container workspace path.
- Uses an idle long-running command suitable for IDE attachment.
- Sets `ASTRO_OLLAMA_HOST=http://host.docker.internal:11434`.
- Adds `host.docker.internal:host-gateway` for Linux compatibility.
- Publishes container port `8501` with Docker selecting an available host port.
- Does not start Ollama or Streamlit automatically.

The local generated override adds only host-specific mounts and values,
especially the linked worktree Git metadata mount.

### Dev Container configuration

The Dev Container configuration:

- Uses the same Compose `app` service.
- Selects the mounted worktree as `workspaceFolder`.
- Runs the host initialization script before Compose starts so the local
  override exists.
- Performs the editable package installation after container creation.
- Reuses the existing container when reopened.
- Does not define a second image, dependency list, or application service.

### Worktree helper

A repository-owned shell helper accepts a task or branch name and:

1. Checks that Git, Docker, and Docker Compose are available.
2. Sanitizes the input into safe, deterministic branch, directory, and Compose
   project slugs.
3. Rejects existing branch or path collisions without modifying them.
4. Creates the branch and linked worktree under `.worktrees/<slug>`.
5. Resolves the worktree and Git common-directory paths.
6. Generates the worktree-local Compose override and environment metadata.
7. Builds and starts the uniquely named Compose project.
8. Reports commands for IDE attachment, CI, Streamlit startup, port discovery,
   and project cleanup.

The helper must avoid deleting or overwriting an existing branch, worktree, or
container project.

### Documentation

The contributor documentation explains:

- Host prerequisites: Git, Docker with Compose, and a running host Ollama with
  the required models.
- Automated helper usage.
- Manual Dev Container usage from an existing checkout or worktree.
- How to run the full quality gate.
- How to start Streamlit and discover its mapped URL.
- How to stop a single worktree's Compose project without removing source or
  branch state.

## Workflows

### Helper-driven agent workflow

An agent invokes the helper with a task slug. After validation, the helper
creates the linked worktree, prepares its local Compose metadata, starts the
project, and prints all connection details. The agent works and tests inside
that container. Starting or stopping another worktree project has no effect on
this project.

The quality gate is:

```bash
./scripts/run_ci_checks.sh full
```

The live application command is:

```bash
streamlit run app.py --server.address 0.0.0.0
```

After Streamlit starts, the helper or documented Compose command resolves the
published port and reports `http://localhost:<assigned-port>`.

### Manual Dev Container workflow

A developer opens a checkout or linked worktree and chooses "Reopen in
Container." The host initialization step derives the worktree-specific project
and Git-mount metadata. The Dev Container then starts and attaches to the same
Compose `app` service used by the helper.

The initialization script is idempotent: rerunning it updates only generated,
gitignored metadata for the current worktree.

### Cleanup workflow

Container cleanup targets an explicit Compose project name and removes only
that project's containers and network. It does not remove the worktree,
branch, Chroma data, logs, or other source-tree files. Worktree and branch
removal remain separate, explicit Git operations.

## Error handling

The helper fails before creating state when prerequisites, names, or paths are
invalid. After worktree creation, later failures retain the worktree and print
the exact recovery or cleanup command rather than deleting source implicitly.

Errors must identify:

- Missing or unreachable Docker/Compose.
- Existing branch, worktree path, or conflicting Compose project.
- Failure to resolve or mount linked-worktree Git metadata.
- Image build or container startup failure.
- Failure to discover the dynamically published Streamlit port.

An unavailable host Ollama does not block container creation or CI. The live
application startup documentation includes a host Ollama health check and a
specific remediation message. Secrets from a host `.env` are not copied into
new worktrees automatically; users may create a worktree-local `.env` when
needed.

## Testing and acceptance criteria

The implementation is accepted when all of the following are demonstrated:

1. A clean development image builds successfully.
2. The container reports Python 3.11 or newer and imports the editable
   `astro_agent` package.
3. `./scripts/run_ci_checks.sh full` passes inside the container.
4. Two linked worktrees run concurrently as distinct Compose projects with
   distinct containers, networks, and host Streamlit ports.
5. `git status` and a test commit work inside both linked-worktree containers,
   including repository-owned hooks.
6. Streamlit responds successfully through each reported host URL.
7. Both containers can reach the shared host Ollama endpoint.
8. CI remains usable when host Ollama is stopped.
9. Rebuilding after only a source change reuses the dependency-install layer.
10. Helper-driven and manual Dev Container workflows produce equivalent Python,
    dependency, mount, environment, and CI behavior.
11. Stopping one project does not stop or remove the other project's resources
    or alter either worktree.

Automated tests should cover slug generation, collision detection, generated
metadata, prerequisite failures, and command construction without requiring
real container creation. A documented integration smoke test covers Docker,
parallel worktrees, Git access, dynamic ports, Streamlit, and host Ollama.
